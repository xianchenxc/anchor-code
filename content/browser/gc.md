title: 垃圾回收
---

垃圾回收（GC, Garbage Collection）是 JavaScript 引擎自动管理内存的机制。开发者不需要手动 `free` 内存，但仍需要理解“对象为什么会被回收、为什么有时回收不掉”。

## 1. 什么是垃圾

在 JS 里，**无法从根对象继续访问到的值**，会被视为垃圾候选对象。

常见根对象（Root）包括：

- 全局对象（浏览器里的 `window`）
- 当前执行栈与作用域链中的变量
- 引擎内部仍在引用的对象（如正在执行的任务）

只要对象还能从根对象“可达（reachable）”，就不会被回收。

## 2. 核心算法：标记清除（Mark-and-Sweep）

现代 JS 引擎（V8、SpiderMonkey 等）核心思想是标记清除：

1. 从根对象出发，标记所有可达对象
2. 未被标记的对象判定为不可达垃圾
3. 回收不可达对象占用内存

优点：能处理循环引用问题。  
这也是为什么“循环引用”在现代引擎里通常不会直接造成泄漏（前提是整体不可达）。

## 3. 分代回收思想（重点）

大多数对象“生得快、死得也快”，因此引擎会把堆内存按代划分：

- **新生代（Young Generation）**：存放新创建对象，回收频率高，速度快
- **老生代（Old Generation）**：存放存活时间长的对象，回收频率低但成本更高

常见过程：

- 对象先进入新生代
- 多次 GC 后仍存活 -> 晋升到老生代

这就是“分代假说”在 JS 引擎中的应用。

## 4. V8 常见回收类型（面试高频）

### Minor GC（新生代）

- 主要针对新生代
- 频率高、单次暂停相对短
- 常与复制算法（Scavenge）配合

### Major GC / Full GC（老生代）

- 主要针对老生代，必要时处理全堆
- 更重，暂停时间可能更明显
- 通常会组合标记、清除、整理等步骤

## 5. 为什么会出现卡顿

GC 需要占用 CPU，且某些阶段会导致主线程暂停（Stop-The-World）。  
如果在动画、滚动、输入等关键时刻触发较重 GC，就会产生掉帧和卡顿。

典型触发因素：

- 短时间创建大量临时对象
- 长生命周期大对象持续增长
- 内存碎片与老生代压力过高

## 6. 常见内存泄漏场景（前端）

1. **全局变量或缓存无上限增长**
2. **定时器未清理**（`setInterval`、重复注册 `setTimeout`）
3. **事件监听未移除**（尤其是组件销毁后）
4. **闭包意外持有大对象**
5. **Detached DOM 引用**（DOM 已移除但 JS 仍引用）
6. **Map/Array 长期累积且不淘汰**

## 7. 工程实践：如何降低 GC 压力

- 减少热点路径中的对象分配（避免无意义临时对象）
- 复用对象与数组（在性能敏感区域）
- 及时解绑事件、清理定时器、释放引用
- 对缓存设置容量上限与过期策略（如 LRU + TTL）
- 大列表使用虚拟滚动，减少 DOM 与对象常驻

## 8. 如何排查内存问题（Chrome DevTools）

常用面板：

- **Memory**：Heap Snapshot、Allocation instrumentation
- **Performance**：观察时间线中的 GC 事件与长任务

常见排查流程：

1. 执行操作前拍一次 Heap Snapshot
2. 执行可疑操作（切页、开关弹窗、反复渲染）
3. 再拍快照对比对象增长
4. 关注 `Detached HTML...`、闭包链、持续增长集合
5. 修复后复测，确认曲线回落

## 9. 常见误区

- **“JS 有 GC 就不会内存泄漏”**：错误。可达但无用的对象仍可能长期占内存。
- **“手动置 null 一定能解决泄漏”**：不一定，关键是是否还有其他引用链。
- **“循环引用一定泄漏”**：现代标记清除下不成立，只有可达链保留才会泄漏。
